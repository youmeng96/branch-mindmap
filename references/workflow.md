# Branch Map Workflow

## 1. 自动启用判定

加载 Skill 后先判断任务是否可执行：

- 有文件修改、工具调用、调查、设计、编码、测试、部署或多步决策：启用。
- 纯知识问答、简单翻译、无需行动的解释：跳过，不创建文件。

## 2. 初始图

默认节点：

- 根节点：任务目标。
- 2–6 个主要步骤。
- 已知决策点。
- 已知风险和预期产物。

不要一次生成几十个细枝末节。导图先帮助用户建立全局方向，再随证据展开。

## 3. 检查点

只在关键点更新：

| 时机 | 写入内容 |
|---|---|
| 任务开始 | 目标、初始步骤、假设 |
| 计划变化 | 新分支、被否决方案、原因 |
| 重大修改前 | 影响范围、风险、回滚点 |
| 验证后 | 测试结果、失败证据、下一步 |
| 用户编辑后 | 读取最新 revision，采纳用户结构 |
| 完成 | 最终产物、遗留风险、任务状态 |

## 4. 决策等待

当分支取决于用户偏好、预算、授权或不可接受的风险：

1. 创建 `decision` 节点。
2. 写清选项、影响、代价和推荐。
3. 写 `decision` 检查点。
4. 停止依赖该决策的执行动作，等待用户回答。

不要为了保持自动执行而替用户做高影响选择。

## 5. 写入门禁

所有写入者都必须带当前 revision：

- 浏览器 `PUT /api/map` 使用 `expected_revision`。
- CLI `add`、`update`、`checkpoint` 使用 `--expected-revision`。
- Agent 写图前先运行 `status` 或重新读取 `map.json`。
- revision 不一致时停止写入，读取最新 JSON 后合并。
- 无法合并时创建 `decision` 节点，不直接覆盖。

## 6. 失败恢复

| 情况 | 处理 |
|---|---|
| map 丢失 | 搜索现有任务图；仍不存在时询问是否初始化 |
| 多个候选 map | 展示任务标题、task_id 和修改时间，让用户选择 |
| JSON 损坏 | 保留原文件，报告错误，不覆盖 |
| 校验失败 | 修复结构后再次运行 `validate` |
| 脚本或 Python 缺失 | 停止写入并输出文本版导图 |
| 静态 HTML 未落盘 | 要求导出 JSON 或启动本地服务 |
| `409 Conflict` | 刷新、合并、重新校验后再写 |
| 用户删除分支 | 遵守删除或 rejected 状态，不擅自恢复 |

## 7. 用户编辑

浏览器编辑器可以：

- 新增子节点和同级节点。
- 修改标题、摘要、类型、状态和产物。
- 删除子树。
- 折叠和展开分支。
- 保存到 `map.json`。
- 导出 JSON 和 Mermaid。

拖拽排序和多人协作不在 v0.1 范围内。

## 8. 冲突处理

- 浏览器每次保存带 `expected_revision`；CLI 写入带 `--expected-revision`。
- CLI 与服务共享跨进程锁，避免 TOCTOU。
- 服务器与最新 revision 不一致时返回 `409`。
- 浏览器不得自动覆盖；用户应刷新并重新合并。
- Agent 写图前必须重新读取文件。
- 同一字段冲突时停止自动合并，创建 `risk` 节点并请求用户判断。
- Agent 更新用户编辑过的节点必须显式 `--allow-editor-overwrite`，且保留 `origin: "editor"`。

## 9. 完成

任务完成时：

- 已完成节点设为 `done`。
- 放弃的分支设为 `rejected`。
- 阻塞项设为 `blocked`。
- 记录产物路径。
- 写 `done` 检查点。
- 验证 `map.json`。
- 保留导图作为工作记录，不自动提交到 Git。
